# CyberFortress — Product Requirements Document (PRD)

**Project Name:** CyberFortress  
**Project Type:** Interactive Cybersecurity Learning Platform  
**Version:** 1.0  
**Target Users:** Students, beginners, and general users interested in cybersecurity  
**Platform:** Web Application  
**Frontend:** HTML, CSS, JavaScript  
**Backend:** Python + Flask  
**Database:** SQLite  
**Charts:** Chart.js  
**Version Control:** Git + GitHub  

---

## 1. Product Overview

### 1.1 Product Description

CyberFortress is an interactive web-based cybersecurity learning platform designed to help beginners understand common cybersecurity threats and basic security practices.

Unlike a traditional educational website that only provides text-based information, CyberFortress allows users to **interact with cybersecurity concepts through simulations, quizzes, security checks, challenges, and visual dashboards**.

The platform follows a simple learning cycle:

> **Learn → Try → Answer → Get Feedback → Earn Points**

The main purpose is to make cybersecurity education more **interactive, practical, understandable, and engaging**.

---

# 2. Problem Statement

Many beginners learn cybersecurity through theoretical material such as articles, slides, and lectures.

The problem with this approach is that users may understand the definition of an attack but may not know how to recognize or respond to it in a realistic situation.

For example, a user may know what phishing is but still click on a suspicious email.

CyberFortress addresses this problem by allowing users to interact with simplified cybersecurity scenarios.

### Problems CyberFortress aims to solve

- Lack of practical cybersecurity learning for beginners.
- Difficulty identifying phishing attacks.
- Lack of understanding of password security.
- Limited understanding of MFA.
- Difficulty understanding how security monitoring works.
- Lack of beginner-friendly cybersecurity challenges.
- Cybersecurity concepts can appear complicated to new learners.

---

# 7. Feature 1 — Phishing Awareness Simulator

## 7.1 Purpose

Teach users how to identify suspicious emails and phishing attempts.

---

## 7.2 User Flow

The user opens the phishing simulator.

The website displays a sample email.

Example:

> **From:** security@example-login.com  
> **Subject:** Your account will be deleted!

The user receives two options:

- **Safe**
- **Suspicious**

The user selects an answer.

The system then provides feedback.

---

## 7.3 Example Suspicious Indicators

The simulator may highlight:

- Suspicious sender address.
- Urgent language.
- Unknown links.
- Requests for passwords.
- Spelling mistakes.
- Fake security warnings.
- Unusual attachments.

---

## 7.4 Functional Requirements

**FR-PH-01:** The system shall display sample emails.

**FR-PH-02:** The system shall allow users to classify an email.

**FR-PH-03:** The system shall determine whether the answer is correct.

**FR-PH-04:** The system shall display an explanation after the answer.

**FR-PH-05:** The system shall award points for correct answers.

**FR-PH-06:** The system shall record the user's result.

---

## 7.5 Example Feedback

If the user chooses **Suspicious**:

> Correct! The email contains several phishing indicators, including an unusual sender address and urgent language.

If the user chooses incorrectly:

> Not quite. Look carefully at the sender address and the request for account information.

# 8. Feature 2 — Attack & Defense Simulator

## 8.1 Purpose

Demonstrate how a basic cyber attack can be detected and mitigated.

This feature will use **completely simulated attacks** and will not perform real attacks against external systems.

---

## 8.2 Basic Flow

```text
Attacker
   ↓
Target
   ↓
Security Monitoring
   ↓
Detection
   ↓
Defense
   ↓
Attack Blocked
```

---

## 8.3 Example Scenario

### Scenario: Multiple Failed Login Attempts

The simulator displays:

```text
Attempt 1 → Failed
Attempt 2 → Failed
Attempt 3 → Failed
Attempt 4 → Suspicious
Attempt 5 → ALERT
```

The system detects unusual activity.

The user can then select a defense:

- Block IP
- Enable MFA
- Monitor activity
- Ignore

The system explains the result.

---

## 8.4 Functional Requirements

**FR-AD-01:** The system shall display a simulated attack scenario.

**FR-AD-02:** The system shall show attack steps sequentially.

**FR-AD-03:** The system shall display security detection.

**FR-AD-04:** The user shall select a defensive action.

**FR-AD-05:** The system shall show the result of the selected defense.

**FR-AD-06:** The system shall provide an explanation.

# 9. Feature 3 — Password Security Checker

## 9.1 Purpose

Teach users about password strength.

The system should clearly warn:

> **Do not enter your real password. Use a sample password for this demonstration.**

---

## 9.2 Password Analysis

The system can check:

- Password length.
- Uppercase letters.
- Lowercase letters.
- Numbers.
- Special characters.
- Common/simple patterns.

---

## 9.3 Example

User enters:

```text
password123
```

System displays:

```text
Strength: Weak

Problems:
✓ Too common
✓ Easy to guess
✓ Could be stronger

Suggestion:
Use a longer and more unique password.
```

---

## 9.4 Strong Example

```text
River!Cloud7-Mango
```

Possible result:

```text
Strength: Strong

✓ Good length
✓ Contains different character types
✓ More difficult to guess
```

The checker should avoid claiming that a password is absolutely "unbreakable."

---

## 9.5 Functional Requirements

**FR-PS-01:** The system shall provide a password input field.

**FR-PS-02:** The system shall warn users not to enter real passwords.

**FR-PS-03:** The system shall analyze the sample password locally where possible.

**FR-PS-04:** The system shall display password-strength feedback.

**FR-PS-05:** The system shall identify common weaknesses.

**FR-PS-06:** The system shall provide improvement suggestions.

# 23. Security Requirements

Because CyberFortress itself is a cybersecurity project, the application should demonstrate good security practices.

### Requirement 1 — Password Protection

User passwords must be hashed before being stored.

### Requirement 2 — Input Validation

User inputs should be validated on the backend.

### Requirement 3 — No Real Credentials

The application must clearly tell users not to enter real passwords or sensitive information.

### Requirement 4 — Safe Simulations

All attacks should be simulated.

CyberFortress must not perform actual attacks against external systems.

### Requirement 5 — No Real Personal Data

The project should avoid collecting unnecessary personal information.

### Requirement 6 — Authentication Security

Sessions should be handled securely.

### Requirement 7 — Error Handling

The application should not expose sensitive backend errors to users.

---

# 40. Final Product Vision

The final CyberFortress experience should feel like a **small cybersecurity training center inside a website**.

The user should be able to:

```text
        LEARN
          ↓
       PRACTICE
          ↓
       SIMULATE
          ↓
        SOLVE
          ↓
        SCORE
          ↓
       IMPROVE
```

The key idea is **not to build a real hacking platform**. Instead, CyberFortress should safely demonstrate cybersecurity concepts through controlled simulations and beginner-friendly challenges.

### One-line project vision

> **CyberFortress is an interactive cybersecurity learning platform that helps beginners learn, practice, and test their security knowledge through safe simulations, challenges, and security monitoring demonstrations.**
